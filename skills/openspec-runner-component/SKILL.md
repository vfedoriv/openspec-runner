# Delegated component handoff

Use this workflow when a teammate owns an assignment in a shared Store. Read the workflow guide at the installed package path reported by `openspec-runner --help` for checked command syntax and complete input schemas. Distinguish this mode from an ordinary repository-local managed feature: an imported component stops at receipt export. The coordinator owns acceptance, PR merge evidence, shared completion and post-merge archival.

Require the explicit feature ID, Store checkout path, assignment ID, owner and repository identity. Inspect `component inspect <feature> --store PATH --repository ID --assignment ID --owner LABEL --json`; show the approved base, task settings, Store contract revision, fingerprint and local resources. Preview/import with `component import` using its exact token and inspected `historyRevision` as `--expected-head`. Import resumes the same binding after an interrupted reservation. Only `--file RESOURCES` can overlay terminal/worktree adapters and worktree root; it cannot change models, tasks, setup or checks. The CLI never fetches or pushes: Git retrieval and publication are explicit handoffs requiring the user's authorized scope.

The assignment's immutable materialized context and approved revision take precedence over a newer mutable Store checkout. Use `component status <feature> --store PATH --repository ID --change CHANGE --json` to inspect the local binding, pinned context paths and last inspected coordination history. Stop and reconcile a revoked assignment with the coordinator. Do not silently replace the contract, reapprove locally, edit the binding or call `reconcile` to adopt changed scope. Scope/settings changes need a revised committed plan, renewed shared approval and a new assignment.

For a replacement assignment for the same bound change, create a fresh independent implementation clone at the replacement's exact approved base with its committed plan and available authoritative Store history. Create fresh local resources and a machine repository map, then run normal inspect/import with the new ID, owner and inspected history revision. A worktree sharing the old Git common directory shares its binding and cannot replace it. Retain the old clone/runtime/worktrees/logs for outstanding jobs or evidence. Version 1 shared approval renewal applies feature-wide: historical merges remain inspectable, but old-approval results are not automatically live milestones. Reconcile approved plans/assignments and inspect coordinator blockers; old final review/consent does not carry forward. There is no automatic rebinding, approval inheritance or reset/retirement API.

Run existing `status`, `launch`, `worker`, `report` and `integrate` commands for the imported change. Launch only ready tasks without model/effort/harness/base overrides; approved settings already bind them. After all tasks are integrated, run a fresh `feature review CHANGE`. Inspect its structured report and worker exit. Repair blocking findings with `feature fix`, integrate the repair, then review again within the assigned repair limit. Respect the existing coordination skill's terminal ownership, interrupted integration, retry and cleanup rules.

At a clean, reviewed, verified integration commit, preview `component export <feature> --store PATH --repository ID --change CHANGE --outcome completed --dry-run --json`. Export with `--confirm TOKEN --expected-head SHA --id ID --operation ID --output RECEIPT`, using the real preview token, an available inspected Store history SHA, explicit receipt identities, and an external output file. A token identifies the snapshot; it is not approval for publication. For blocked/failed work, export that outcome with a concrete `--reason`; no fabricated result SHA or passing checks are required. Retrying export preserves the exact identity and bytes. Publish the returned result branch in its implementation repository and the exact receipt bytes on a separate Store submission branch using normal Git operations. Hand the coordinator the result SHA, receipt ID and Store handoff ref.

Never use local `feature approve --final` or `feature archive` to finish this assignment. A successful export is a handoff claim, not coordinator acceptance or shared completion. An unmerged component PR blocks shared completion; accepted components and combined review only make them ready for delivery. Preserve local runtime/worktrees for unresolved verification or process recovery; another machine reconstructs shared status from committed Store history, not your session files.
