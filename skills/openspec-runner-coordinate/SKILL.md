---
name: openspec-runner-coordinate
description: Coordinate local OpenSpec batches or managed features, or shared Store assignments, acceptance, tuple reviews, Git merge evidence, exact completion and archive delivery.
---

Identify the mode first. A shared feature has an explicit Store checkout, feature ID and machine repository map. Resume with `coordination status <feature> --store PATH --map MAP --json`. A local imported assignment belongs to `openspec-runner-component`; use `component status` and stop at receipt export, never the local final-approval/archive steps below. For a repository-local change:

First run `openspec-runner status <change> --json`. If it returns a feature lifecycle phase and approval history, use the managed lifecycle below. Otherwise preserve the explicit batch-approval workflow in the remaining instructions.

## Shared Store coordination

Read the workflow guide at the installed package path reported by `openspec-runner --help` for checked schemas, command options and Git handoffs. Status derives committed records on the manifest's named coordination branch; inspect its planning/implementation roots, acceptance, delivery, archive, blocker and next action. It does not fetch remote branches or prove live hosting-provider PR state. Supply explicit machine map paths; do not infer repositories or main/master branches from the Store selector.

Preview approval/assignment with `--dry-run --json` and retain exact token/head/IDs. `approve`, `complete` and `archive-approve` require actual user consent with `--approved-by`; possession of a token/current checkout or a general implementation request is not that consent. One active assignment covers one whole component. Dependencies gate issuing assignments by exact accepted/merged upstream commits. `revoke` records a concrete reason before reassignment. Receipt `import` preserves the owner's bytes and identity, including failed/stale claims; it does not accept them. Retrieve the named result branch and exact commit with explicit authorized Git handoffs before `accept`. Acceptance independently checks the assignment, plan, completed tasks, component review and approved setup/checks without needing the owner's sessions/worktrees.

All components accepted unlock `review --stage combined`. Preview the tuple, obtain fresh exact-tuple reviewer attestation in `--file`, and record it with the real token/head. Blocking correctness/security/spec/verification findings return to the responsible owner. Changed component results invalidate downstream unmerged acceptance and tuple review. An approved repair allowance authorizes in-scope component corrections; new task scope/settings need committed revised plans and renewed shared approval.

For reassignment of a change already bound locally, hand the owner the new assignment and exact approved plan/base/history for a fresh independent implementation clone with fresh resources and repository map, followed by normal inspect/import. A worktree sharing the old Git common directory shares its binding. Retain the old clone/runtime for outstanding jobs or evidence. Version 1 approval renewal applies feature-wide: historical merges remain inspectable, but old-approval results do not automatically remain live dependency milestones. Inspect every blocker and reconcile approved plans/assignments before proceeding; further implementation of merged components requires revised plans and renewed approval. Old final review and completion consent do not carry forward. Do not reset bindings or infer approval inheritance.

Combined review makes components ready for delivery. Every required PR must merge before shared completion. Record `merge` only with the full locally retrieved delivery commit on its declared branch, merge style, HTTP(S) PR URL and explicit operator attestation. A rewritten result whose accepted path blobs/modes/deletions differ needs `accept-delivery` with fresh exact-commit review and independent approved checks before merge recording. Git-only evidence is an attested PR outcome, not a network query. Once every merge is recorded, run fresh `review --stage final` against the merged tuple. Then preview `complete`, present that exact tuple/review and optional archive scope, obtain user consent, and record it. Shared completion is delivery completion and does not require archival. An unmerged PR always blocks it.

Archive separately after completion. Preview and explicitly approve the selected component IDs, Store inclusion and explicit Store canonical branch using `archive-approve`, unless final completion already approved the unchanged scope. `archive-prepare` creates local post-merge branches and records prepared evidence. Publish/review/deliver those branches explicitly, then use `archive-deliver` for each exact canonical delivery; prepared status alone is not archived. Store archival currently needs repository-root `openspec/changes/<shared-change>`; nested Store roots require component-only scope or a reviewed plan move/renewal.

Retry interrupted immutable operations with the original IDs, payload, token and expected head; do not relaunch failed/running checks with a new ID to erase uncertainty. Use `archive-inspect` for retained checkouts/receipts. `archive-recover` requires inspection, exact target and explicit operator attestation before adopting already-produced output without rerunning OpenSpec. Publication rejection requires inspecting remote history and reconciling the declared branch; never force-push authoritative history. Offline reconstruction uses committed Store records plus the explicit local repository map. Preserve unresolved local journals and worktrees for recovery.

## Managed features

Resume using `openspec-runner feature status <change> --json`; it works before task artifacts exist and after archival. Respect its blocker and next action. A saved plan approval authorizes implementation, integration, review, and in-scope repairs; do not ask again for each routine batch. Missing/stale approval requires returning to planning. Do not edit runtime state directly.

During implementation, use ordinary `status`, `launch --tasks ... --dry-run --json`, `launch`, and `integrate`. Select ready tasks from the execution plan, respecting dependencies, exclusive work, and the concurrency limit. Managed launch uses frozen per-task settings; omit harness/model/effort/base overrides. Inspect worker reports and successful exits before integrating. Continue through ready batches in this conversation; there is no unattended scheduler.

After all tasks are integrated, preview and launch `feature review <change> [--dry-run] --json`. This creates a fresh reviewer session and isolated checkout. In manual-terminal mode, present its returned supervised worker command exactly once. Inspect `feature status` until the report and exit receipt are available. Do not infer completion from a quiet terminal.

If the review has correctness, security, spec, or verification blockers, preview and launch `feature fix <change> [--dry-run] --json`. One repair attempt covers the current blockers. Integrate its verified result with `feature integrate <change> --attempt <id> --json`, then launch another fresh review. Allow at most two repair rounds by default. Advisory style/improvement findings do not trigger automatic repairs. At the limit, on a failed/blocked session, or when scope must change, stop and show the evidence for user direction. After that direction, use `--retry` for an unsuccessful review/repair attempt; retries consume repair rounds. Extending the limit requires another reviewed plan approval.

For interrupted repair integration, inspect the worktree, resolve/stage conflicts, then use `feature integrate --continue`, or explicitly abort with `--abort`. For a lost supervisor or interrupted preparation, `feature recover <change> --attempt <id>` only records a provably interrupted job; it never redispatches. Ambiguous process/terminal ownership requires inspection. Keep feature job worktrees and their saved logs for diagnosis; their paths remain in status.

When the fresh review has no blockers, run `feature approve <change> --final --dry-run --json` and `feature archive <change> --dry-run --json`. Present the branch, checks, review evidence, advisory findings, and archival/spec-synchronization scope. Ask the user to approve this exact final snapshot. Record consent with `feature approve <change> --final --confirm <token> --json`; do not use the token without approval. Then run `feature archive <change> --json`. If interrupted, inspect recorded state and rerun archive; it resumes rather than creating a duplicate archive/commit. Never manually declare completion when archival or post-archive checks failed.

Completion means the integration branch is reviewed, verified, and contains the archived change. Deliver its branch and archive receipt. Merging into a target branch or publishing a PR is separate. Normal task cleanup may leave resources requiring inspection; show them without treating cleanup failure as feature failure. The existing per-resource cleanup consent rules below still apply to managed features.

## Unmanaged batches and shared resource rules

Run `openspec-runner status <change> --json` and show ready tasks with their assignments. Confirm one batch harness from the preview; use `--agent claude` or `--agent codex` when selecting it explicitly. Before previewing, verify every selected task is ready. A dependency selected in the same batch is not satisfied until it has been integrated; if any selected task is blocked, show the unmet dependencies and required sequence instead of running `launch`. Preview an entirely ready batch using `openspec-runner launch <change> --tasks 2.1,2.2 --agent <harness> --dry-run --json`, then run the same command without --dry-run only after user approval. Do not start a continuous scheduler. Claude previews show unsupported calling-session inheritance and its configured permission policy; supply `--default-model` or explicit task models.

Inside Herdr, the runner creates one workspace per task without moving focus. Inside stablyai/orca, `terminal: orca` (or auto-detection through `ORCA_TERMINAL_HANDLE`) creates a dedicated background terminal per supervised worker. Use `worktrees: orca` to create task worktrees through the app too; worktree selection is independent of terminal selection. The registered Orca CLI, runtime, and runner must share the local host and filesystem. Use the runner for dispatch and cleanup; Orca's `worktree rm` can delete branches. Other Orca terminals, including app-created initial shell tabs, block cleanup until inspected and closed. Runtime changes or stale handles require inspection; do not adopt replacement terminals automatically. Outside either environment, present the returned supervised worker commands for separate user terminals. Do not substitute an unrequested background launcher. Use `attach` for existing sessions. A dry-run that fails because restricted subprocess execution suppresses command output may be repeated with the necessary execution permission because it creates no resources; never treat that retry as approval for a real launch. A timeout or blocked/ambiguous real launch is not permission to resubmit or start another session. Inspect saved pane identifiers; after restart, use the exact saved Codex or Claude resume recipe only when identity was confirmed. A worker's normalized structured report and real exit receipt, not terminal activity indicators or a Claude result event, establish an eligible result.

Review the report, verification evidence, commit, and worktree before integrating the user's selected results with `integrate <change> --tasks ...`. Integration changes checkboxes only in the dedicated integration worktree. Stop at conflicts or failed checks; inspect and resolve before `integrate --continue`, or explicitly abort with `integrate --abort`. Dependents remain blocked until integration completes.

A worker reporting blocked or failed has stopped implementation. New workers run a supervised Codex or Claude CLI process and exit after their final turn; report acceptance alone does not prove process exit. Inspect the saved worker exit receipt, immutable harness/session identity, normalized terminal evidence, and log. Request a new attempt with `retry` when the user wants further implementation. Do not resume finished workers in removed worktrees.

After successful integration, inspect the cleanup summary: automatic cleanup closes verified owned terminals and removes eligible task worktrees; completion of all planned tasks also sweeps obsolete attempts. Keep branches and the integration worktree. For every `confirmation-required` item, show its exact path, reasons, changed files, and terminal activity, then ask the user whether to delete it/close the reviewed terminal. Warn that uncommitted and ignored files in the directory will be discarded. No response means keep. Apply only approved candidates with `cleanup <change> --tasks ... --attempt ID --confirm TOKEN --json`, or `cleanup <change> --all --attempt ID --confirm TOKEN --json` for final-sweep candidates. Fresh changes require a fresh review. Never fabricate consent or use tokens without user approval.

For skipped resources, resolve ownership or worker-exit uncertainty before retrying. Close manually opened terminals only when the user authorizes it; confirm their closure before worktree deletion. Retry leftovers with `cleanup --all --dry-run --json` and then the approved cleanup operation. `cleanup: manual` keeps terminals/worktrees until explicit cleanup. Cleanup errors do not invalidate successful integration. Final integration-branch delivery and OpenSpec archival require explicit user action.
